MAINTENANCE RULES
  1. Common public UI belongs in site.css / site.js.
  2. Page-specific UI and behavior stay in that page's CSS/JS unless cross-page reuse is proven.
  3. Do not delete code because it merely looks unused. Check HTML -> CSS -> JS -> dynamic class/id -> other pages first.
  4. Before changing CSS, inspect hover/focus/is-selected/nth-child/::before/::after/transform/filter/box-shadow/background and media queries.
  5. Before changing admin code, inspect Supabase requests, shared snapshots/events, auth, RPC and DOM ownership.
  6. Prefer one source of truth over repeated overrides or duplicate requests.
  7. Keep changes zero-regression: current rendered result and behavior must stay the same unless the user explicitly requests a change.
  8. Use full-file integrated replacements for user-facing code changes whenever practical.

CACHE RULE
  Local CSS/JS references use one shared query-version value per deployment.
  Current baseline version: v=20260905-4
  When deploying a changed CSS/JS bundle, increment the version consistently across all local CSS/JS references.

GIT RULE
  .gitattributes defines text/binary handling to reduce line-ending noise.
  Do not perform a mass renormalization together with feature work. If needed, do it in a separate commit.

SECURITY BOUNDARY
  Frontend files do not prove backend safety by themselves.
  RLS, RPC, SECURITY DEFINER, FK, triggers and Storage policies must be reviewed separately in Supabase before backend changes.
